# Account recovery and verification abuse-control runbook

**Status:** [PR #23](https://github.com/eghosa001/Animal-app/pull/23) merged on 2026-11-06. PostgreSQL and Flutter CI verified; production SMTP and real Android/iOS tests are pending. Part of AUTH-03 and AUTH-04; [issue #10](https://github.com/eghosa001/Animal-app/issues/10) stays OPEN for staff MFA, device/session management and privacy requests.

## Product behaviour

- **Forgot password:** A signed-out user enters an email, sees the same generic confirmation for an existing, unknown or disabled account, then receives a random email code if their account is active and eligible. Code expires in **20 minutes**.
- **Confirm reset:** User enters email, code, a policy-compliant new password and confirmation. The server consumes the code atomically. Old access and refresh JWT sessions become invalid. The user must sign in again.
- **Verify email again:** The existing verification request now enforces a per-account cooldown and hourly count. Previous unconsumed verification codes are invalidated upon issuance of a fresh code. An already verified account cannot redeem an arbitrary code.
- **No secrets in APIs:** Reset code only in the email, not API response, logs, database plaintext, URL query string or app persistent storage.
- **User interface:** Flutter **Profile → Forgot password?** and **Resend verification code**. The recovery page uses a deliberately separate form, validates confirmation and does not save new passwords.

## Routes

| Endpoint | Method | Body | Result |
|---|---|---|---|
| `/api/v1/auth/password-reset/request` | POST | `{"email":"user@example.com"}` | Generic HTTP 200 for valid address, whether account exists |
| `/api/v1/auth/password-reset/confirm` | POST | `{"email":"...","token":"...","new_password":"..."}` | HTTP 200 when token accepted; 400 with safe validation messages otherwise |
| `/api/v1/auth/resend-verification` | POST | `{"email":"..."}` | Generic HTTP 200, with cooldown |
| `/api/v1/auth/verify-email` | POST | `{"email":"...","token":"..."}` | Accept exactly one still-valid code; generic invalid token response |
| `/api/v1/auth/login` and `/api/v1/auth/refresh` | POST | Existing JWT credentials | Per-IP throttled; passwords changed since token issuance cannot be reused |

Django validates new passwords using `AUTH_PASSWORD_VALIDATORS`; accounts cannot reset back to their immediately previous password. Older passwords/password history is **not** yet enforced.

## Security design

1. Codes are generated by `secrets.token_urlsafe(32)` and stored only as a SHA-256 digest. The token has high entropy; comparisons use `hmac.compare_digest`.
2. Recovery challenges have one-use `used_at`, 20-minute `expires_at`, per-account 10-minute issuance cooldown and maximum 3 per hour. Email verification resends use their own 10-minute cooldown and 3/hour limit. Database row locking prevents concurrent replays.
3. DRF `ScopedRateThrottle` provides additional per-client-IP limits for login, registration, verification, resend, reset request/confirmation and JWT refresh. Protect the originating IP via a correctly configured trusted reverse proxy; do not trust arbitrary forwarded headers.
4. **Shared Redis Django cache is mandatory when `DJANGO_DEBUG=false`**; a process-local cache is allowed only in development. Deployers must configure `REDIS_URL` to a securely isolated and monitored Redis service. The API will not start without Redis configuration in non-debug mode.
5. `SIMPLE_JWT["CHECK_REVOKE_TOKEN"]=True` embeds a password-derived claim and checks it for access and refresh. Password changes also blacklist all outstanding unexpired refresh tokens, so old devices lose session authority.
6. Minimal `AccountSecurityEvent` audit rows contain event type and user identity but no code or password. Email failures are logged without recipient/token content and must not disclose account existence in the API response.
7. Do not automatically equate successful reset with independent seller or business verification. Seller reviews and animal listings remain independently governed.

## Rollout and dependencies

- Requires Django migration `accounts.0003_password_resets_and_security_events`; rollback should preserve existing users and password hashes.
- The installed Simple JWT version must support `CHECK_REVOKE_TOKEN` and enforce password-changed checks on token refresh. Existing tokens issued **before enabling this setting will be rejected** and users must log in again.
- Configure a production transactional email provider with SPF, DKIM, DMARC and verified sending domain. The project defaults to console email in DEBUG and SMTP otherwise, but **no live email provider has been configured**.
- Use HTTPS for both Flutter and the API. No raw code in browser URLs, public app analytics or client event logs.
- Set Redis key prefix and environment isolation for staging/production; monitor 429 and SMTP failure rates.
- Do **not** turn on production staff moderation until MFA, support and incident controls are approved and tested. This PR does NOT deliver staff MFA, device management, account export or deletion.
- Purge expired security challenges according to a reviewed data retention schedule. Automatic purging and vendor email deliverability monitoring remain separate release tasks.
- Confirm account recovery on a real Android phone and iOS device, including lost connection, unverified account, expired code, email delays and a reset initiated on another device.
